## G01 · P1：源码包缺少迁入的验收资产

证据：[MANIFEST.in](../../MANIFEST.in) 只显式纳入若干根文档、工具 Python
文件与 JSON fixtures；未纳入 `validation/`、`docs/`、`AGENTS.md` 和
`tools/README.md`。本次在独立副本离线构建源码包，实际成员检查证实上述
路径均缺失，但依赖这些文件的测试和工具已经进入包。

解包后运行：

```bash
python tools/check_core.py --pattern test_real_second_point_assets.py
```

结果为 `Ran 3 tests`、`FAILED (errors=3)`；均因找不到
`validation/chan-real-second-point-manual-0.9.10.json`。
依赖位置见 [资产测试（整改后位置）](../../validation/tests/test_real_second_point_assets.py)。
该产物是从当前工作树生成的本地候选包，不是从 PyPI 下载的已发布 1.0.0。

影响：独立 Git checkout 可以验收，当前源码分发包却无法完成相同验收，
接手维护者不能仅凭源码包重建迁入的冻结标签。

整改：明确源码包的开发复现范围，将完整测试所需人工表、冻结输入、
协作规范、计划和工具说明列入打包清单；在 CI 解包 sdist，离开原 checkout
运行完整测试，并验证可以从该 sdist 构建和隔离安装 wheel。保留本次失败证据。

## G02 · P1：发布标签没有与包版本绑定

[流水线](../../.github/workflows/test-and-release.yml) 接受全部 `v*` 标签；
两个发布 job 只检查标签前缀，随后构建和上传。
[版本测试](../../tests/test_contracts.py) 仅比较 Python 版本与 pyproject，
没有比较 Git 标签。新 [源码检查入口](../../tools/check_core.py) 也只检查双处版本。

触发示例：在包版本仍为 1.0.0 的提交上推送 `v1.0.1`，现有版本测试不会
因此失败，GitHub Release 可被标成 v1.0.1 而装载 1.0.0 产物；PyPI 对
重复版本的拒绝不能替代发布前版本校验。本次仅检查路径，未推送任何标签。

整改：所有上传前强制校验标签、双处版本、wheel/sdist 元数据一致；
不匹配时立即失败，并用错误标签样本验证发布 job 不会执行。

## G03 · P2：已验收产物没有直接传递到发布

[测试 job](../../.github/workflows/test-and-release.yml) 构建并验收 wheel，
旧环境下载该 wheel；但 [Release job](../../.github/workflows/test-and-release.yml)
和 [PyPI job](../../.github/workflows/test-and-release.yml) 分别再次执行 `uv build`。
发布 job 没有下载已测产物，也没有自动逐文件对比或摘要闭环。

影响：当前流程保证了同一个源码提交被构建，尚未自动保证上传的是已经
验收的那份产物。本次没有观测到已发布文件内容错误；1.0.0 的手工内容
核验记录保留，不能据此断言未来每次独立构建都等价。

整改：集中生成一次待发布 wheel/sdist，完成验收后按产物摘要传递给
Release 与 PyPI；或者对重新构建的结果执行自动内容等价校验并留存收据。

## G04 · P2：1.0 稳定性规则仍指向候选版契约

[AGENTS](../../AGENTS.md) 与 [CONTRIBUTING](../../CONTRIBUTING.md) 要求
1.0 后遵守 API 契约；但 [API.md](../api.md) 标题仍为候选版、适用版本
仍为 0.13.x，算法输出变更规则也只描述 0.x.x。
[pyproject](../../pyproject.toml) 同时保留 Beta 分类。

影响：维护者可以找到接口冻结规则，但无法直接判断 1.x 的算法修正、
字段扩充、默认值调整与破坏兼容分别应如何编号和验收。

整改：使当前 API 文档覆盖 1.x，写清主/次/修订版本的变更边界，区分
API 稳定与输入修订、尾部修订、算法修正。保留旧契约历史，维护当前生效规则；
候选或 Beta 描述是否继续适用，应与正式发布定位一致说明。

## G05 · P2：唯一进度表混合历史缺口与当前结论

进度来源唯一是优点，但若干单行把早期“尚未实现”和后续已交付逐版追加。
例如 [因果中枢行](../缠论理论逐一实现计划.md) 开头仍写尚未实现身份谱系，
后文又登记谱系、升级、移交、重组与因果图已交付，最后保留多轮真实标注缺口。
[自动一类行](../缠论理论逐一实现计划.md) 仍保留早期阶段缺口描述。

影响：“部分”状态本身合理，但读者需自行重建时间线才能确定当前剩余问题；
不能把开头旧缺口或末尾新版本单独当作完整当前结论。

整改：仍只维护 §6 一张表，每行先写当前能力、当前缺口与最新证据，再链接
§9 历史版本记录；区分未实现、已实现但缺独立真实样本、原文歧义及输入前提。
不要为了清表将证据不足改成已完成，也不要另建第二套理论进度表。

## G06 · P2：本地治理尚未成为可检出的交付版本

本次 `git ls-files` 确认新 `AGENTS.md`、`tools/check_core.py` 和
`tests/test_check_core.py` 尚未跟踪。当前 HEAD 与本地 origin/main 引用均为
`8239243`，外层 gitlink 也仍指向此基线；新 CI 命令和文档同样未提交。

影响：工作树内已经可用的分离规则，尚不能由另一台机器通过对应提交完整
取得。这是待交付状态，不代表基线 8239243 的原有 CI 已损坏。

整改：将评估后确认的治理变更在核心库形成独立提交，推送并核验该提交的
现代、旧环境和产物检查；外层再升级到远端已存在的指针。工程治理本身
不要求发布新的 PyPI 版本，也不自动重发 1.0.0。
